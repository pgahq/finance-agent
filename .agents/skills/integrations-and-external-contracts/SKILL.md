# Integrations and external contracts

## HTTP triggers

Both routes share bearer auth against SSM `/finance-agent/enrich-invoice-api-token` (`ENRICH_INVOICE_API_TOKEN`). Callers send `Authorization: Bearer <token>`.

### `POST /create-invoice`

Intercom Data Connector entry point for new supplier invoices (no existing Workday record).

Request body:

```json
{ "conversationId": "1234567890" }
```

This is a new Intercom-only contract. Direct-upload bodies
(`fileName` / `contentType` / `fileContent`) are not accepted.

Flow:

1. `GET {INTERCOM_API_BASE_URL}/conversations/{id}?display_as=plaintext` with `INTERCOM_ACCESS_TOKEN` and `Intercom-Version: 2.14`
2. Collect every `application/pdf`, `.docx`, and `.xlsx` attachment from `source` + conversation parts (a Word or Excel file is detected by its OOXML MIME type, or by extension when Intercom sends `application/octet-stream`; legacy `.doc`/`.xls`, images, and other types are ignored, and a conversation with none of the accepted types → 400)
3. Download signed CDN URLs as **raw binary** immediately (URLs expire ~30 minutes; host allowlisted to Intercom CDN; combined max 20MB)
4. Upload each file to S3 (`new-invoices/{requestId}/{index}-{sanitizedFileName}`)
5. Build a text transcript PDF of the same conversation and upload it once under `new-invoices/{requestId}/`. The file name is `pga_corp_accounts_payable_<YYYY>_<MM>_<DD>_<conversationId>.pdf`, using `created_at` in America/Chicago (current Central date if `created_at` is missing). The PDF includes the source email (subject with HTML stripped, then body) and `conversation_parts` whose `part_type` is `comment` or `note` and whose body is non-empty, in API order. Omit Intercom **Message delivery failed** bounce notes (body contains that phrase, or an SMTP diagnostic such as `smtp;550 5.7.129`). Assignments, attribute updates, custom actions, and close events are omitted. Notes are labeled `Note`. The header is one title: `Conversation with {custom_attributes.Brand}` when Brand is set, otherwise the conversation `title`, otherwise `Conversation`. If rendering or this upload fails, return 500 and do not invoke processors.
6. Resolve **assignee email** from the same conversation GET: among `conversation_parts.conversation_parts`, use the **last** part with `part_type === "custom_action_started"` and take `author.email` (any `author.type`). Forward as `assigneeEmail` on each processor invoke.
7. Async-invoke `CreateInvoiceProcessor` with `emailContext` (`emailFrom` / `subject` from the attachment’s message when applicable; `plainTextBody` is the **source email body plus every non-empty `conversation_parts` body**, joined with blank lines in API order — including internal notes, not only the message that holds the PDF; omit Intercom **Message delivery failed** bounce notes so SMTP codes such as `550` are not treated as company or coding tokens; keep AP auto-replies and human notes; `conversationParts` is the same minus the source email body; `adminConversationParts` keeps only internal notes (`part_type` `note`) whose author `type` is `admin`, so supplier replies, bots, and AP replies sent to the supplier are excluded), shared `assigneeEmail`, `conversationCreatedAt` from Intercom `created_at`, and `conversationPdf` (`s3Key` / `fileName` of the transcript). When `INVOICE_ATTACHMENT_CLUSTERING_ENABLED` is `true`, invoke **once per conversation** with `attachments` (every uploaded file's metadata); otherwise (default, including a missing SSM parameter), invoke **once per vendor PDF**. When it is `shadow`, invoke once per vendor PDF and then, best-effort, once more per conversation with `attachments` and `shadow: true` (report-only clustering Slack; never writes). Processor Lambda async retries are off (`MaximumRetryAttempts: 0`); a thrown error Slacks once and does not re-run.
8. Flag off: each vendor PDF creates a separate Workday invoice. Flag on: the processor classifies and clusters attachments (see the `invoice-attachment-clustering` skill) and creates **one Workday invoice per invoice cluster**; leftover clusters fan out to separate processor invokes. Workday lists attachments newest-first, so SOAP `Attachment_Data` is sent in reverse (transcript first, vendor invoice last) and Workday shows the vendor PDF(s) first and the conversation transcript last. Enrichment sees vendor PDFs only, never the transcript. A re-triggered conversation updates or skips instead of creating a second invoice for the same supplier invoice number: newer documents or messages update the existing Draft invoice, nothing-new re-triggers skip, and non-editable invoices skip with a manual-review note. Exceptions (see that skill): a different real supplier or a canceled invoice re-sent with a newer document creates a new invoice. A create stops and reports an error if Workday says the supplier invoice number is already in use; it does not retry on the fallback supplier and is no longer flagged as a possible duplicate. Return HTTP status to the Data Connector
9. Workday `Invoice_Received_Date` on each new supplier invoice is set from the Intercom conversation `created_at` (mailbox receipt), formatted as `YYYY-MM-DD` like other SOAP dates

**Workday assignee on create:** `CreateInvoiceProcessor` looks up `assigneeEmail` in the daily **Worker Assignment For AP Agent** custom report cache (`employee` documents, exact email match). Report **Workday ID** values must be Worker WIDs (`WorkerObjectType`: `WID`, `Employee_ID`, or `Contingent_Worker_ID`; we send `WID`). When a Worker WID is found, SOAP `Submit_Supplier_Invoice` sets `Supplier_Invoice_Data.Work_Queue_Information_Data.Assignee_Reference` (not a top-level `Supplier_Invoice_Data` field); when the part is missing, email is blank, or there is no cache match, **omit** `Assignee_Reference` (create still succeeds). If Workday returns a validation fault that references assignee, submit **retries once** without `Assignee_Reference`. Cache job: `CacheEmployees` / `CacheEmployeesProcessor` fetches `AP_AGENT_WORKERS_CUSTOM_REPORT_PATH` in `ap_agent_workers_report.ts` (`wdw-7212/Worker_Assignment_For_AP_Agent`, `customreport2` JSON). Report columns: `Workday_ID`, `Primary_Work_-_Email`, `Active_Status`, `Full_Legal_Name`, `Preferred_Name`, `Employee_ID` (logged on each sync). All parseable report rows are cached; `metadata.active` is a boolean derived from `Active_Status` (and terminated when present). Assignee lookup requires `active !== false`. Create-invoice Slack and Workday notes display `preferredName`, falling back to Full Legal Name (`name`) when Preferred Name is blank or not yet cached. Prune removes employees no longer in the report snapshot.

**Supplier hints from the email context:** `enrichInvoiceFromAttachments` scans the whole email context — `emailContext.subject` and `plainTextBody` (for Intercom, the source email plus every non-empty conversation part, any `part_type` or author, except Intercom Message delivery failed bounce notes; for `/enrich-invoice`, the Workday inbound email) — for Workday Supplier IDs (`S-` plus 4–6 digits, any case) and `Supplier:` / `Vendor:` lines (colon, or a dash with spaces; embedded IDs are stripped from names). Everything scanned becomes a hint, but only IDs that also appear in `emailContext.conversationParts` (Intercom notes and replies) can be authoritative. An ID found only in the source email or the Workday inbound email is a findSuppliers candidate and never overrides the invoice PDF — a sender could otherwise pick a real cached supplier. `/enrich-invoice` has no `conversationParts`, so its hints never replace an assigned supplier. IDs are resolved in code by exact match on cached `metadata.supplierId` (`resolveSupplierIdHints`). An exact match is injected as authoritative over the invoice PDF only when every extracted ID resolved to that same supplier and its ID appears in a conversation part; if any other hinted ID is unresolved, the hints are called incomplete and the match is only a findSuppliers candidate. Two or more distinct matches tell the model to return ambiguous/uncertain. An ID missing from the cache is listed as not a match; a failed lookup asks for a findSuppliers result whose Supplier ID matches exactly. Hinted names only set the first findSuppliers query, and are dropped when the ID match is authoritative. 

**Supplier name fallbacks and candidate notes:** when the model reports `not_found`, code re-checks the supplier by exact name, then by a distinctive printed-name word that only one cached supplier has (confidence 0.8), and otherwise lists up to 5 possible suppliers in the `Supplier:` work-queue note without applying them (the default supplier is still the one submitted). Rules, thresholds, and logs are in `data-and-state-changes` (supplier name evidence and distinctive-word fallback).

`CreateInvoiceProcessor` looks for a purchase order number in the email/filename and fetches that PO **before** enrichment when one is present. A PO number needs at least one digit after `PO` (`normalizePurchaseOrderNumber`), so a label such as `PO Number` is not read as `PO-NUMBER`. If the PO is only on the PDF, enrichment extracts it and the processor fetches the PO afterward. An AP Intercom note PO wins, then the one PO named by the message that carried the invoice, then the PDF PO (below). When no note or single email/conversation PO applies and enrichment extracts a *different* PO number than the email/filename hit, submit uses that matched PO for company and lines — not the early PO. If that late load misses, submit drops the early PO and falls through to **Default OCR Company** (`Company_Reference_ID` `Default_OCR_Company`, or `WORKDAY_DEFAULT_COMPANY_WID` when set) and skips early PO lines.

**PO named in an Intercom note wins over the invoice PO:** suppliers often print a stale PO, so AP adds a note such as "Don't use the PO on the invoice. use PO-413672 Line 7". `findNotePurchaseOrders` reads `emailContext.adminConversationParts` only (teammate-written internal notes; an AP reply to the supplier, a supplier reply, or the source email never overrides) for `PO-XXXXXX` / `PO# XXXXXX` / `PO number XXXXXX`, each optionally followed on the same line of text with no sentence end (`.`, `;`, `?`, `!`) between by `Line N` / `Ln N` / `line #N` / `Line Number N` / `Line No: N`; a range or list such as `Line 7-8` / `7/8` / `7 and 8` / `7 to 8` / `7 through 8`, `Line 0`, or a second line reference in the same clause (`Line 7, not Line 8`, `not the PO line 8`; a clause ends at a sentence end, a line break, or the next PO number) names no line. `htmlToText` normalizes CRLF, turns block tags (`br`, `p`, `div`, `section`, …, attributes may quote `>`) into line breaks, and strips comments, known tags, and unknown letters-only tags (`o:p`, `v:shape`, custom tags) that have no attributes or real `name=` attributes; other bracketed text such as `<PO 413672>`, `<PO-413672>`, `<Arrow Exterminators>`, `<a@b.com>`, and `a < b` survives (a supplier name hint drops its surrounding brackets). A PO is *rejected* when words such as `not`, `don't use`, `instead of`, `old`, or `wrong` sit right before it, or `is old` / `is wrong` right after it. A note PO is *tied* to an invoice number (`invoice N`, `Inv # N`, `invoice no: N`, `invoices N, M and K`; the number needs a digit and three characters and is never a PO or a date) named earlier in the same sentence ("Invoice 69962682: use PO-413672 Line 7"), or, failing that, the next one in the same sentence ("PO-413672 Line 7 for invoice 69962682"); a sentence end, line break, or `;` ends the scope. Invoice numbers compare without punctuation, an `INV` prefix, or leading zeros. `selectNotePurchaseOrder` never uses a rejected PO. When any note PO is tied to an invoice number (a conversation with several invoices), only the single unrejected PO tied to this invoice's extracted supplier invoice number overrides, and an invoice the notes do not name keeps its own PO; when the notes tie no PO to this invoice (including when its number was not read), the Workday note says so, e.g. `Purchase order: The Intercom note names PO-413672 for invoice 69962682, not this invoice (69962699); kept PO-411406.` Otherwise (AP usually writes just the PO when the conversation has one invoice) it uses the only note PO, or, when the notes name several, only when they reject the invoice PO and exactly one other unrejected PO remains ("not PO 411406, use PO-413672"); otherwise nothing overrides. The invoice PO is the PDF PO from enrichment; before enrichment, and after it when the PDF has none, the PO in the subject, source email body, or filename stands in for it. The chosen note PO is prefetched before enrichment; when Workday does not return it, the email/conversation PO and then the fallback PO below are prefetched instead, and a PO Workday did not return is not fetched again. When the note PO loads from Workday, it replaces the invoice PO for company, memo, notes, Slack, and line coding, and the invoice PO is not loaded. When it does not load, or no note PO is chosen, the one PO that the message that carried this attachment (`emailContext.messageBody`, the Intercom source email or conversation part body, plus `messageSubject`, which only the source email has, so a reply never inherits the thread's first subject; the subject and source email when `messageBody` is missing) and the filename name (`findSolePurchaseOrderNumber`, leaving out every PO an AP note mentions; text naming several distinct POs names none, so a multi-invoice email never overrides) wins over the PDF PO when Workday returns it. Older messages in the thread never count, so an earlier invoice's PO or an AP reply such as "reference PO-500001 on future invoices" cannot beat the PO printed on a new invoice. The Workday note records `Purchase order: Used PO-414373 from the email or conversation instead of PO-411406 on the invoice.`, or `PO-414373 from the email or conversation was not found in Workday; used PO-411406 instead.`, and create Slack shows `*PO #* → PO-414373 (from email or conversation; invoice shows PO-411406)`. Otherwise the PDF PO is used, else the subject/source email/filename PO (the source email is `plainTextBody` minus the trailing `conversationParts`; when that boundary is missing, or admin parts exist without `conversationParts`, the body is not used), else a PO in the visible text of conversation parts that no AP note mentions in any form (a PO AP mentions in a note is never a fallback); the Workday note says when the note PO was not found. A line number counts only when the notes name exactly one line for that PO; the PO is then narrowed to the line whose `lineOrder` (Workday `Line_Number`) matches before availability marking and line merge, so every invoice line codes from and links to it. A line not on the PO is ignored with a note. When **Default OCR Company** is used, no PO lines are coded, so the note line is not claimed in the Workday note or Slack. The Workday note records `Purchase order: Used PO-413672 Line 7 from the Intercom note instead of PO-411406 on the invoice.` (or `instead of PO-411406 in the email` when the PDF shows no PO and the email does); the `(from document)` PO note still shows the invoice value. Create-invoice Slack shows `*PO #* → PO-413672 Line 7 (from Intercom note; invoice shows PO-411406)` (`email shows` for an email PO), and appends `· coded from PO, not linked to PO lines` whenever a closed-PO or consumed-line fallback dropped `Purchase_Order_Line_Reference`.

PO line parsing (`parsePurchaseOrderLines`) merges line `Worktags_Reference`, **Additional Worktags** (`Purchase_Order_Line_Worktags_Data`), and split `Worktag_Reference` rows into a deduped passthrough list. When the PO line has splits, matched invoice lines also submit `Supplier_Invoice_Split_Line_Data` copied from the PO split rows (amounts and worktags). Accepts both legacy `Service_Line_Data` / `Goods_Line_Data` and Get PO `*_Replacement_Data` field names. Org passthrough (`Organization_Reference_ID` / `Custom_Organization_Reference_ID`, e.g. venue `VENU-...`) is matched by value against related LOB, not blocked by ID type alone, so venue/event coexist with LOB. Additional worktags always copy: shared/uniform PO tags apply to unmatched lines (splits need exact match), splits inherit line-level venue/event/custom missing on that split, shared fund/cost-center/LOB stay on the parent when splits lack that dimension, and PO fund/cost-center/LOB replace fallback (email/real scalar still wins ties). **Exception on a cost-center availability retry** (`applyCostCenterFallback`): lock the fallback cost center so PO passthrough does not restore the rejected PO cost center, then keep a single fallback Cost Center — on every split when any split already carries a cost center (parent stripped), otherwise on the parent. Synthetic remainder lines merge without PO line matching so they do not inherit a `Purchase_Order_Line_ID` or split rows; shared additional PO worktags still overlay afterward.

**One worktag per type:** Workday rejects a line or split row that carries two worktags of the same Workday type ("Only one worktag for each type is allowed for each document line"). Before every submit, `collapseWorktagsToOnePerType` keeps the first worktag per type on each parent line and each split row (scalar, email, and fallback tags come first), except that a real LOB replaces a fallback LOB (`FALLBACK_LOB_ID` / `Default_Line_Of_Business`) so the fallback never beats the PO LOB. Non-organization tags are typed by SOAP ID type (`Fund_ID`, `Cost_Center_Reference_ID`, `Custom_Worktag_*`). Organization tags share `Organization_Reference_ID`, so only LOB and event can be typed: the line's own `lineOfBusinessId` / `eventId` / `eventWid`, `LOB-` prefixes and related LOB, and the cached `lob` / `event` documents (`getOrgWorktagKindsByIds`, by WID or LOB `referenceId`, looked up once per submit through `resolveOrgWorktagKinds`). The same cached kinds reach `mergePassthroughWorktagReferences` and split enrichment (`OrgPassthroughContext.orgKinds`), so an unprefixed PO LOB is recognized there too: it replaces a fallback LOB, is not added beside a real one, and is not copied onto splits. Venue and other custom organization tags are not cached, so they are kept unless identical. Dropped tags are logged per line and split, and a successful submit records the fallback `kept one worktag per type (dropped …)` (up to five values) in the Workday note and Slack. If Workday still returns this fault, submit retries once with `omitPoPassthroughWorktags`: PO split rows stay (amounts and their own worktags), but PO passthrough is dropped from the parent and is not copied onto splits; the line keeps its scalar fund, cost center, LOB, event, and spend category. The retry records `omitted PO pass-through worktags (kept PO split rows)`. The classifier and the fallback cost center are never used for this fault. On any validation fault, submit logs each line's and split row's worktags as `Type=value` (no attachment data), and `loadPurchaseOrder` logs each PO line's worktags and split worktags (not the raw Get PO response) on the create path.

**Closed or Pending Close POs:** `parsePurchaseOrder` reads header `Purchase_Order_Document_Status_Reference` into `documentStatus` (`Document_Status_ID` plus descriptor). `isPurchaseOrderClosedForInvoicing` is true when either value normalizes to Closed or Pending Close; a missing status reads as open. Workday rejects invoice lines that link to lines on those POs, so create and enrich still use the PO for company, memo PO number, and line coding (worktags, LOB, splits, spend category) but submit with `omitPurchaseOrderLineReference`, which drops every `Purchase_Order_Line_Reference` (including OCR passthrough lines on update). In-memory `purchaseOrderLineId` stays set. If a status was missing or unrecognized and Workday returns "PO that is Closed or Pending Close" while a submitted line carries the reference, submit retries once with the same omit and records the `omitted PO line reference (PO closed or pending close)` fallback. Other `Purchase_Order_Line_Reference` faults (duplicate, canceled, wrong PO or company, closed individual PO line) do not trigger the omit. Either path adds the note and Slack fallback line "PO-XXXXXX is Closed or Pending Close; invoice lines were coded from the PO but not linked to PO lines." Choosing a different open PO is out of scope.

**Enrich PO number:** `EnrichInvoiceProcessor` uses the one PO the inbound email subject and body name (`findSolePurchaseOrderNumber`; several distinct POs name none) over the PDF PO when Workday returns it, and otherwise the PDF PO. The Workday note records `Purchase order: Used PO-414373 from the email instead of PO-411406 on the invoice.` or `PO-414373 from the email was not found in Workday; used PO-411406 instead.`, and enrich Slack shows `*PO #* → PO-414373 (from email; invoice shows PO-411406)`.

**PO supplier:** `parsePurchaseOrder` reads header `Supplier_Reference` into `supplier` (WID, optional `Supplier_ID`, descriptor), and `loadPurchaseOrder` logs it. Workday only lets the PO's own supplier invoice the PO ("You can't select this supplier to invoice this purchase order"), so whenever the chosen PO exists in Workday, create, resend updates, and enrich submit with the PO's supplier instead of the supplier resolved from the invoice. `resolvePurchaseOrderSupplier` (`src/lib/po_supplier.ts`) returns that supplier and how the invoice supplier relates to it: `same` (already the PO supplier; no note), `related`, or `unrelated`. It compares the invoice supplier (resolved name, letterhead name, phone, email, plus the cached `supplier` document's names, alternate names, phones, and emails; an unresolved invoice supplier contributes only what the invoice shows) with the PO supplier (descriptor plus its cached document). Names match only when they reduce to the same set of at least two distinctive words after dropping suffixes such as Inc, Ltd, Mfg, Manufacturing, USA, Group, and Holdings, so "Golf Holdings Inc" never matches "Golf Group LLC". A cached `Company Name` is read whole (it may contain commas). `Alternate Names`, `Phone`, and `Email` are comma-joined lists, as are the invoice phone and email, and are split. Phones match on the last 10 digits. Emails match on a business domain only when the two suppliers' names also share a word; free mail, ISP mail (such as comcast.net), billing platforms, and PGA's own domains are ignored. If the cache lookup fails, only names are compared. The relation only decides the wording: the Workday note says `Supplier from PO: Set to CLUB PRO GOLF GROUP LLC, the supplier on PO-414373.` plus why a related invoice supplier matches, or, for an unrelated one, `The invoice names GOLF GEAR LTD, which does not look like the same company; confirm the PO number.` Slack shows `*Supplier* → descriptor (from PO-XXXXXX)` and, for an unrelated invoice supplier, lists the confirm-the-PO line under *Fallbacks Applied*. Invoices are always submitted as drafts, so AP reviews the change. If Workday still returns the PO supplier fault, submit fails without the classifier; the default supplier is never offered when a submitted line links a PO line. The conversation invoice registry still stores the supplier resolved from the invoice, so resends do not count as a supplier change.

**Consumed PO lines and service dates:** `parsePurchaseOrderLines` also reads each line's `Invoice_Status_Reference`, `Payment_Status_Reference`, and `Close_Status_Reference` (ID plus descriptor), and on service lines `Start_Date` / `End_Date` as `startDate` / `endDate` (`YYYY-MM-DD`). Workday exposes no invoiced amount per line. Production responses carry these as ID values with no descriptor: `Document_Status_ID` "Fully Invoiced" / "Partially Invoiced" and `Document_Payment_Status_ID` "FULLY PAID" / "PARTIALLY_PAID" / "UNPAID" (confirmed from EnrichInvoiceProcessor PO response logs). `isPurchaseOrderLineAvailableForInvoicing` is false when the invoice status normalizes to Fully Invoiced or Over Invoiced, or the close status to Closed or Pending Close; partial, missing, and bare "Invoiced" statuses read as available. Payment status is parsed and logged but does not decide availability: in production, lines are `FULLY PAID` only when also Fully Invoiced, and partly invoiced lines show `PARTIALLY_PAID`. A Fully Invoiced PO keeps header status Issued, so the line invoice status is what marks it consumed. `markPurchaseOrderLineAvailability` debug-logs status counts by status name so tenant values can be checked. The merge prompt appends `poLineSelectionPromptRules`, and create and enrich pass **every** open-PO line to `buildFinalInvoiceLines` with `availableForInvoicing` set (`markPurchaseOrderLineAvailability`); a Closed or Pending Close PO skips this and keeps the invoice-wide omit above, and an invoice with no PO lines keeps the original merge prompt and input. The merge input carries `invoiceDate`, `invoiceServicePeriod` (`extractedServicePeriod`), and each PO line's window and availability. The prompt picks among same-description lines by the period in the line description or service period (month names, quarters, ranges), uses the invoice date only when no period is stated, and never moves to another period's line because the matching one is unavailable; it prefers an available line only when nothing else distinguishes them. After the merge, `markConsumedPoLineReferences` sets `omitPurchaseOrderLineReference` on each invoice line matched to an unavailable PO line: it keeps that line's coding (worktags, splits, spend category) but `buildSubmitInvoiceData` drops that line's `Purchase_Order_Line_Reference`, records the `omitted PO line reference (PO line fully invoiced or closed)` fallback (`consumedPurchaseOrderLine`), and the note reads "Invoice lines that matched lines on PO-XXXXXX already fully invoiced or closed were coded from the PO but not linked to PO lines." **Self-reference guard:** on update, a flagged line keeps its reference when the invoice being updated already links to that PO line (its current `Invoice_Line_Replacement_Data` `Purchase_Order_Line_Reference`), because this invoice may be what consumed it. When the extracted service period names no month, quarter, or date (`statesServicePeriod`; blank or vague text such as "Annual services" counts as none), `alignPoLinesToInvoiceDate` relinks a line whose PO window excludes the invoice date to the single unclaimed PO line that covers it and has the same scalar IDs (cost center, fund, spend category, LOB), the same non-empty passthrough worktag set, and the same split worktags. A missing Start or End date leaves that side of the window open. Unavailable lines are relink candidates too, so an August-dated invoice the model put on an open September line moves back to the consumed August line and then drops its reference. Lines whose extracted description states a period are never relinked, and in every other case the model pick stands.

**Email budget splits:** when the email divides the cost across two or more budgets, matching returns one `emailBudgetSplits` entry per budget (label, the share as a printed `amount`, a `percent`, or `equalShare`, and that budget's own cost center, LOB, fund, event, and spend category). `emailWorktags` then holds only what every budget shares, never one budget's coding, and the company that applies to the whole invoice stays in `emailWorktags.company`; a budget whose own block names a different company carries it in that entry's nullable `company` (the field is required-nullable, never optional: OpenAI strict structured output rejects optional fields). The model never computes amounts. An "Expense Item" named for a budget (e.g. Hotel) is a spend-category hint the model resolves with `findSpendCategories` (hotel stays are the `Lodging` category). `buildEmailWorktags` (`src/lib/email_worktags.ts`) is the one place create and enrich turn the enrichment into `EmailWorktags`; a single entry is the invoice's coding, not a split. `applyEmailBudgetSplits` (`src/lib/invoice_lines.ts`, called from `finalizeInvoiceLines` before related LOBs are filled) replaces the invoice lines with **one amount-only line per budget** (Quantity 0, Unit Cost 0, Extended Amount the budget's share), because Workday split rows carry no spend category. Each line keeps its budget's cost center, spend category, fund, and event; its LOB is the budget's own, else the related default for that cost center (never another budget's LOB, and `constrainEmailLobToRelatedWorktags` checks each line against its own cost center). Several original lines collapse into the budget lines with their distinct descriptions joined by `; ` (capped near 200 characters, then `; and N more lines`) and no line memo. Shares are exact: dollar amounts must equal the merchandise total (amount due less header freight and tax, `expectedMerchandiseCents`) or the amount due itself (`budgetSplitGrossCents`, `expectedAmountDueCents`): an email that budgets the amount due itself uses its amounts as the line amounts and the budget lines carry the header tax and freight (`outcome.headerChargesRolledIn`). `create_invoice` and `enrich_invoice` then submit the header with `taxCleared` and `freightCleared` and no tax or freight amount (the `submit*` values), while the Workday note still shows what the document printed. This matches how AP codes these by hand: lines total the amount due, header tax is zero, and Workday's intercompany amount is the other company's tax-inclusive share. Any other total is rejected naming both figures. Percentages must total 100%, and an even split gives each budget the cent floor with the leftover cents on the last budget (`$100.00` across 3 is 33.33, 33.33, 33.34). The split is not applied, and the lines stay as built, when any of these hold: a PO is loaded or any line carries a PO line, Default OCR Company is used (the lines get fallback coding; the note and Slack still list the budgets as `Budget split review: ... Default OCR fallback coding was applied to the lines`), the invoice is all freight or a freight or tax charge was withheld or the amount due is unreadable, a line has no readable amount or is a credit or discount, the lines do not total that merchandise total, the shares mix kinds or the email states no amount, percentage, or even split ("split between A and B" is flagged, never assumed 50/50), or a budget has neither a cost center nor a spend category. A budget's company is trusted only after `resolveBudgetSplitCompanies` (`reference_ids.ts`) holds it to the invoice company's rule: the code must be coding in the email, match exactly one cached company, and be the code the model claimed; otherwise it is `companyUnverified` and flagged. `budgetCompanyOptions` (`email_worktags.ts`, used by create and enrich) also finds the Company_Reference_ID of the company the header is actually submitted under (the email company, else a cached lookup by WID), because that is what a budget is compared with. A verified budget company that differs from the header's gets that company on its own line (`FinalInvoiceLine.intercompanyAffiliateId`, sent as `Intercompany_Affiliate_Reference` with type `Company_Reference_ID`); if the header company is unknown, no line company is set and the review note says so. Workday's fault for a pairing it does not allow is "... is not configured to allow intercompany transactions with ..." (or names `Intercompany_Affiliate_Reference`); only that fault makes `submitNewSupplierInvoice` and `submitSupplierInvoiceUpdate` retry with every line under the invoice company, and the `omitted line company` item under Fallbacks Applied names each line, amount and company that moved. A budget cost center equal to that budget's own company code is dropped like the invoice company's. An applied split can still carry a `Budget split review:` note (`budgetSplitReviewNotes`) for a budget with no spend category in the email, flagged with the default it landed on. A rejected split where every line is on `FALLBACK_COST_CENTER_ID` and no invoice-wide cost center exists adds that all lines are on default coding. A rejected split writes `Budget split review: ...` to the Workday note and the create Slack `*Line review*` (enrich Slack shows `*Budget split review*`, and `*Coding split*` when applied, and suggests the budgets' cost centers when no invoice-wide cost center exists); an applied split writes `Email budget split (one invoice line per budget): ...` to the note and a `*Coding split*` Slack section, and `lineCount` shows the new line count. Retries that change one worktag (fallback cost center, fallback spend category, related LOB) still apply to every line.

Company priority is:

1. Email-coded company
2. PO company, if a matching PO is available
3. Recommended `different` company from the supplier invoice PDF
4. Default OCR Company

When the default company is used and any invoice lines remain, those lines must use Default OCR fallback worktags (`FALLBACK_COST_CENTER_ID`, `FALLBACK_FUND_ID`, `FALLBACK_SPEND_CATEGORY_ID` / `Default_OCR_Spend_Category`, `FALLBACK_LOB_ID`). Do not keep PO line references, email coding, events, or ship-to on those lines. Invoice notes must not list email worktags in that case; they should say Default OCR fallback coding was applied instead.

## Invoice memos

Create and enrich compose Workday header and line `Memo` values in code after enrichment (`src/lib/invoice_memo.ts`). The structure is supplier identifier, supplier reference, PGA PO, service dates, then an optional short description, separated by single spaces. Example: `Cust 115117 Svc Prd 09/01/26 - 09/30/26 elevator phone line service`; with an order number and a PO, `Acct 1033562 Ord 5914196 PO-414498 Svc Prd 09/01/26 - 09/30/26 monthly software subscription`. Include a token only when that field is present (any combination). Never use `. ` or `|` between fields, and keep punctuation only when it is part of an identifier.

1. **Supplier identifier:** `Acct <account number>`, else `Cust <customer ID>`. Only one is emitted; the account number wins when both are printed.
2. **Supplier reference** (`extractedSupplierReference` plus `extractedSupplierReferenceKind`): one reference, labeled `Ord` (order), `Conf` (confirmation), `Job`, `File` (file or matter number), or `Case`. A legal invoice uses its file, case, or matter number. A reference with no usable kind is labeled `Ref`; a kind-less value that starts with a known label (`Order #5914196`) takes that label. The reference is dropped when it normalizes to the extracted PGA PO. The Workday note records `Supplier Reference (from document): Order 5914196`.
3. **PGA PO:** `PO-######`, from the matched, email, or note PO and otherwise the extracted PO, normalized by `normalizePurchaseOrderNumber`. It sits after the supplier reference and before the service dates, appears once on the header memo and on every line memo, and is left out when no valid PO exists (free text such as `PGA COACHING` is not a PO).
4. **Service dates:** `Svc Prd` plus `MM/DD/YY`; a range is `MM/DD/YY - MM/DD/YY` (spaced hyphen); a whole month stated as `2026 - September` becomes its first and last day; a quarter is `Q4 26`. Dates are read before pay-file sanitizing, so an en or em dash range reads as a range (`09/01/2026 – 09/30/2026`). A label in front of the dates (`Pay Date Range 09/28/2026 - 10/11/2026`, `Week Ending 10/11/2026`) is dropped by skipping up to five leading words until the rest reads as dates, never skipping a word that holds a digit, a month name, or a quarter (so `Sep 28 - Oct 11, 2026` and `Q3 - Q4 2026` stay as printed instead of losing the start of the range); the OCR prompt also asks for the dates without the label. Only whole month names and their usual short forms (`Aug`, `Sept`) count as months, so `Augusta 2026` stays as printed. Text that is not a readable date with a year (`Sept 28 - Oct 2`) stays as printed, with an en or em dash written as a hyphen (`formatMemoServiceDates`).
5. **Description:** a few lowercase words with no ending period, such as `elevator phone line service`. The prompts tell the model to omit PGA, the venue, or the service location and to leave it empty when it would only repeat the supplier name or an identifier. Code lowercases a leading capitalized word (acronyms such as `HVAC` and words with digits keep their case) and drops trailing periods. With identifiers, the description is left out when the memo would pass `INVOICE_MEMO_MAX_LENGTH`; identifiers are never cut. A description-only memo (no identifiers) is sanitized and cut at the limit, so a long line memo never reaches Workday raw.

**The PGA PO is in the memo.** `memoIdentifiersFromEnrichment` takes the matched, email, or note PO (falling back to the extracted PO). A supplier reference that normalizes to that PO is dropped so the PO prints once, and a PO the model copies into the description is stripped, as `PO-######`, `PO ######`, `PO#######`, or `PO #######`. The PO is not required to be found in Workday: when no PO was matched, the extracted (OCR) PO still prints, as it did before #228. AP has not asked for confirmed POs only; if it does, pass a separate printed-PO field set only from the matched PO.

**Open item:** `INVOICE_MEMO_MAX_LENGTH` (500) is a placeholder. AP still has to confirm the check/ACH character limit and which memo field (header or line) feeds checks and ACH before the final length is set.

Pay-file / check print safety:

- Do not emit `|`, `>`, or `<`. Labels we control do not use `#` (`Acct 1033562`, `Job 5914196`). A `#` that is part of a supplier-provided value may stay.
- After compose, keep letters, digits, space, hyphen, period, comma, apostrophe, slash, and `#`; replace other characters with a space.
- `composeSuppliersInvoiceNumber` sets SOAP `Suppliers_Invoice_Number` on create and enrich. It keeps letters, digits, hyphen, period, slash, and `#`; other characters become `-`. Do not rewrite an existing Workday `Invoice_Number` on enrich.

Extraction rules:

- Account number is PGA's customer/sold-to account at the supplier (`Account #`, `Sold To Number`). Skip bank/ABA/ACH remittance account numbers (Cushman `FOR ELECTRONIC PAYMENTS`) in the **OCR prompt only** (`src/prompts/invoice_ocr_prompt.ts`) — there is no code-side remittance parser. Do not use GL, cost center, company code, or the supplier invoice number. Do not strip an `AC-` prefix from a sold-to value such as `AC-1033562`.
- Supplier reference aliases include **Order #**, **Confirmation #**, and **Job #**. Do not map unlabeled Project / `PRJ…` to a reference.
- Customer ID aliases include **Bill-To Customer ID** and **Cust ID**. If it equals the account number, the model leaves it empty; code emits only `Acct` whenever an account number exists.
- Service period may appear inside a line description; the model keeps the document wording and code normalizes the dates.
- The same identifier prefix is applied to every invoice line memo. Header `extractedInformation.memo` and the line-merge prompt must not prepend identifiers — composition strips those tokens (current labels and the earlier `AC 123. Job 456.` form) if the model still includes them.
- **Create** always submits the composed memo, including a description-only memo on a new invoice.
- **Enrich** submits a composed header memo only when identifier tokens exist (a valid PO counts), so a description-only extraction does not overwrite an existing OCR header memo. Workday keeps `currentInvoice.Memo` when `memo` is omitted. Line memos still get the identifier prefix when identifiers exist, and are lowercased and unpunctuated either way.

## Invoice line item descriptions

Workday Line Item Description (`Item_Description`) is the concatenated identifying text from the invoice **row**, not a one-sentence summary and not only the column labeled Description.

The OCR prompt (`src/prompts/invoice_ocr_prompt.ts` Part 9) extracts `descriptionCells` left-to-right (Activity, Resource, SKU, Description, and similar) and asks the model to skip Notes and Comments. `composeInvoiceLineDescription` / `withComposedLineDescriptions` in `src/lib/invoice_lines.ts` then join those cells with ` - ` when any identifying cells exist (the model `description` is fallback only). Code drops empty cells and cells that match the line's printed quantity, unit cost, amount, or a `$` currency value; it does not drop Notes/Comments by column name. A shorter cell is dropped only when a longer cell contains it as a whole token, not as a raw substring. Example: Activity `Ryan Poland` + Description `Project Management` → `Ryan Poland - Project Management`. Header service dates, PO, account, job, and customer ID stay out of Item Description. Freight is classified from the original Description column, then remaining merchandise rows are composed. Compose keeps that original Description when the concatenated cells would classify as freight and the original would not, so SOAP `splitFreightLines` does not reclass the merchandise row.

The short lowercase description is line `Memo`, generated **after** that concatenation (merge prompt), then identifier-prefixed in `composeInvoiceMemo`. After merge, `pinExtractedLineDescriptions` overlays the composed description by line index so the merge model cannot shorten Item Description.

## Model traffic (Vercel AI Gateway)

Every language model and embedding call goes through the Vercel AI Gateway with the AI SDK `gateway` provider (from `ai`), authenticated by `AI_GATEWAY_API_KEY`. There is no direct OpenAI client and no `OPENAI_API_KEY`.

- `src/lib/models.ts`: `defaultModel` is `openai/gpt-5.4` (enrichment matching, classification, clustering, line merge). `getOcrModel()` is `anthropic/claude-haiku-5.5` (`DEFAULT_OCR_MODEL_ID`) and reads only invoice documents; `OCR_MODEL` overrides the model ID. `createLanguageModel` takes a gateway ID (`provider/model`); a bare ID such as `gpt-5.4` is read as `openai/gpt-5.4`, so the `WORKDAY_SUBMIT_REPAIR_MODEL` / `WORKDAY_VALIDATION_FIELD_MODEL` overrides accept either form. Both Workday agents default to `openai/gpt-5.4-mini`.
- Every call is pinned to the model's own vendor with gateway provider options `{ gateway: { only: ['<vendor>'] } }` (`gatewayProviderPin`; `createLanguageModel` applies it through `defaultSettingsMiddleware`). Invoice PDFs and supplier data go to OpenAI for `openai/*` models and never to a gateway fallback host such as Azure, Bedrock, or Vertex. A vendor outage fails the call instead of failing over.
- `src/lib/rag.ts`: `createEmbedding` calls `embed()` with `gateway.embeddingModel('openai/text-embedding-3-small')` and the same pin. Keep that model: stored vectors and the pgvector index are 1536-dimension `text-embedding-3-small` vectors, and a different model needs a full re-embed.

### Invoice enrichment: Haiku OCR, then gpt-5.4 matching

`enrichInvoiceFromAttachments` (create and enrich) makes two model calls and merges them into the unchanged `InvoiceEnrichmentResult`, so callers, line building, and scoring do not change.

1. **OCR** (`extractInvoiceDocuments` in `src/lib/invoice_ocr.ts`): `getOcrModel()` with `tools: {}`, the PDF and image parts, and the document roles. It returns `InvoiceOcrSchema` (`src/prompts/invoice_ocr_prompt.ts`): every `extracted*` field (including `extractedLineSubtotal` and `extractedPartialPayment`, below), `invoiceLineQuantityDisplayed`, `extractedInvoiceLines` (with `tableNumber` and `sectionLabel`), the payment terms name, `printedSupplier` (name, street and remit-to address, phone, email, tax ID, website, memo), and `printedBillTo`. It sends no `temperature`, because Claude Haiku 5.5 rejects sampling parameters (`getAiResponse({ temperature: null })`). Anthropic structured outputs allow at most 16 union-typed (nullable) and 24 optional parameters, so the OCR schema uses required strings and arrays where empty means not printed, and only `quantity`, `hasDiscount` and `tableNumber` are nullable. `normalizeInvoiceOcrResult` turns the empty values back into `null`. Keep new OCR fields within those limits; `invoice_ocr.test.ts` counts them. It does not see the email, PO, or supplier hints. With no PDF or image it is skipped and the document fields stay empty.
2. **Matching** (`invoiceMatchingPrompt`, `InvoiceMatchingSchema`): `defaultModel` with the lookup tools and the OCR JSON as text, plus the email context, reference directory, supplier hints, PO, and existing supplier and company. It gets no file parts. It returns `supplier`, `companyVerification`, `emailSummary`, `extractedPaymentTerms.workdayId` (findPaymentTerms on the OCR name), `emailWorktags`, and `emailBudgetSplits` (below).
3. **Merge** (`mergeInvoiceEnrichment`): OCR wins for every `extracted*` field and for `supplier.extractedInformation` / `companyVerification.extractedInformation` (from `printedSupplier` without `remitToAddress`, and `printedBillTo`). The payment terms keep the OCR name with the matching `workdayId`.

**Due date (`Due_Date_Override`).** `extractedDueDate` is a required OCR string (no union or optional slot), so the counts in `invoice_ocr.test.ts` do not change. The prompt (Part 3.5) takes only a date printed as the due, payment due, or pay-by date, never one computed from terms such as "Net 30", and empty for "Due on receipt". `normalizePrintedDate` accepts exact ISO, US `M/D/YY` or `M/D/YYYY` with one separator, or a real month name with a four-digit year (two-digit numeric years are 20YY), and returns `null` for anything else. `enrichInvoiceFromAttachments` leaves it out of the matching prompt. Create, resend updates, and enrich pass it as `dueDate` next to `invoiceDate`; `buildSubmitInvoiceData` sends it as ISO `Due_Date_Override` (the WSDL field is `xsd:date`; the docs' "MM/DD/YYYY" text is the same as on `Invoice_Date`, which is also sent as ISO) after re-checking it is a calendar date; the processors also re-normalize it with `normalizePrintedDate`, and the note says `unreadable, not sent` only when a caller passes a non-empty value that cannot be read (OCR already maps one to `null`, which behaves as no printed due date). It replaces the current override. The current override is resent (normalized to `YYYY-MM-DD` when it is a recognizable xsd:date string, `$value` wrapper, or the UTC-midnight `Date` strong-soap builds; otherwise unchanged, never dropped) with no usable extracted date, when the extracted date is earlier than the submitted `Invoice_Date` (including the first-of-month default), and when it is more than `MAX_DUE_DATE_DAYS_AFTER_INVOICE` (180) days after it; the last two add a `dueDate` fallback `due date not applied (…)`. The retry after Workday rejects the extracted date also resends the current override, except on the payment-schedules fault (`isPaymentSchedulesOverrideError`), where `clearDueDateOverride` sends none (`omitted due date and the current override (payment schedules)`). `dayMonthYearReading` (`src/lib/due_date.ts`, which also owns the 180-day limit) compares the extracted invoice and due dates read month/day/year with the same dates after exchanging month and day; when only the exchanged pair is plausible, `formatDueDateNotes` adds `The printed dates may be day/month/year: ...` with that reading. It never changes what is sent. `isDueDateValidationError` matches only "Due Date must not be earlier than Invoice Date", "override the invoice due date" (payment schedules), or an `Xpath:` ending at `Due_Date_Override`. When the extracted date was sent, `getValidationFallbackField` returns `dueDate` without the classifier and the retry drops it (`omitted due date`); a later fault on that retry goes to the normal repairs, and an override the agent did not extract is removed only by the payment-schedules retry. Payment terms are still sent with the override. The Workday note's `Due Date (from document)` line explains a fallback, so `dueDate` fallbacks are left out of the note's "Fallback values applied" list; Slack shows `*Due Date*` (or `not applied`) plus the fallback label.

**Several invoices in one PDF (warning only).** One file is one invoice: the classifier, OCR, and submit read the first invoice of a file (KNIGHT JV / LevelBlue sent two PDFs of seven monthly invoices each, one per page, and only page 1 of each was entered). OCR returns `invoiceNumbersInDocument`, a required string array (no union or optional slot) of every separate invoice number printed in the supplier invoice document; Part 6.5 of the OCR prompt excludes numbers an invoice only mentions (prior or credited invoices, statement aging rows) and the numbers of non-invoices (credit memo, statement, quote, packing slip, delivery ticket, receipt), keeps a statement or invoice with receipts or charge slips attached as one invoice (golf course statements),, keeps a multi-page invoice or remittance slip as one invoice, and tells the model to read Parts 1 through 9 from the first invoice only. This rule applies to every OCR read, so `enrich_invoice` also reads the first invoice of a bundle but does not warn: an AP-keyed invoice 2 with the whole bundle attached would be enriched from invoice 1 (follow-up: compare the Workday invoice's supplier invoice number with `invoiceNumbersInDocument`). `normalizeInvoiceOcrResult` trims and drops blanks (none is `null`), `mergeInvoiceEnrichment` copies it, and `multiInvoiceReview` (`src/lib/multi_invoice_pdf.ts`) turns two or more distinct numbers (compared after `sanitizeSuppliersInvoiceNumber` and upper-casing, with the entered `extractedSuppliersInvoiceNumber` always counted and listed first) into `<file> appears to contain N invoices (<numbers>); only <entered> was entered. Enter the rest manually.` At most ten numbers are listed, then `and N more`. `create_invoice` puts that sentence first in the Workday note as `Multiple invoices in one PDF: ...` (create and resend update), and passes `multipleInvoices` to Slack, which shows a `*Multiple invoices in one PDF*` section on every create, update, and skipped-resend post (and a created headline of `from a PDF with more than one invoice` unless an amount mismatch already owns the headline). It never splits the file or creates more than one SUPIN, and a single invoice or a reader that returns no list adds nothing. The note is built before submit and describes the invoice entered, so a repair retry cannot make it false. Enrich does not read it. The original supplier PDFs are not committed as fixtures (public repo); `multi_invoice_pdf.test.ts` generates seven-page PDFs with the same invoice numbers.

An OCR failure throws, like the old single call. There is no fallback to `gpt-5.4` for OCR. Document extraction rules (Parts 3–9) live in the OCR prompt; matching and coding rules live in `src/prompts/enrich_invoice_prompt.ts`.

Create-invoice Slack **errors** show the Workday `Message` plus prior submit attempts — not SOAP dumps. Remaining invoice details (`fileName`, `s3Key`) still appear as JSON; `conversationUrl` stays a footer link. Enrich Slack **errors** include `workdayId` in that JSON plus a not-authorized `note` when the task is not authorized; the Workday footer link uses `workdayId`. Create-invoice Slack **success** uses the same human layout as enrich (`*Changes*`, fallbacks, `*Prior submit failures*`). The Workday **Invoice Number** (`SUPIN-XXXX`, SOAP `Invoice_Number`) is in the headline and as the first Changes bullet, plus a small JSON of `invoiceNumber` / `invoiceWID` / `fileName` / `conversationTranscriptFileName` / `conversationId` / `lineCount`. `conversationTranscriptFileName` is present when the conversation transcript PDF was attached. If Get has no `Invoice_Number`, omit that number from the create headline, Changes bullet, and JSON. Enrich success already puts that number in the `processed \`SUPIN-XXXX\`` headline and repeats it as `*Workday Invoice*`. When Slack has an invoice WID (`invoiceWID` on create/enrich success, `workdayId` on enrich error), add a footer `<url|View in Workday>` and, when an invoice number is also present, make the Changes bullet number a Slack link. URL: `{WORKDAY_UI_BASE_URL}/{WORKDAY_TENANT}/d/inst/deeplink/{WID}.htmld` (`https://impl.workday.com` in implementation, `https://www.myworkday.com` in production). Omit the Workday link when the WID, UI base URL, or tenant is missing. Do not use `Supplier_Invoice_Reference_ID` (`SUPPLIER_INVOICE-3-…`) for Slack. After create, Get the invoice by WID and read `Invoice_Number`. Enrich uses Get `Invoice_Number` only — omit the Slack invoice number if Get does not return it. Sanitized SOAP throws keep a `Validation_Fault` object so enrich skip-registry classification still matches, and keep `serializedError` for a future threaded dump once a Slack bot token exists. Successful Workday submits that retried after a validation fault also include `priorFailures` on create and enrich Slack success.

Every `create_invoice` / `create_invoice_shadow` Slack **error** carries the Intercom custom-action starter (`assigneeEmail`) as `triggeredByEmail` and renders `*Triggered by* Name (email)` right after the error text (email alone when no name), outside the JSON details; only the main create failure looks up `triggeredByName` in the employee cache, and a failed lookup never blocks the alert.

`composeSuppliersInvoiceNumber` follows the HQ invoice naming convention. The date is the document invoice date (`YYYY-MM-DD`), not the day of submit.

- A printed supplier invoice number that is not the same as the account number is submitted as printed (after the character rules above).
- No distinct invoice number, but an account number: sanitized account number plus `MMMYY`, with no extra hyphen (`54875-48235` on 2022-04-01 → `54875-48235APR22`). The same account and invoice number, ignoring spaces, `#`, and hyphens, is not a distinct invoice number (`20-1183-01` in September 2026 → `20-1183-01SEP26`).
- Neither number: the first four letters of the supplier name (letters only, uppercase; a shorter name stays shorter) plus `MMDDYY` (`Safari` on 2022-04-01 → `SAFA040122`). Prefer the name extracted from the PDF, then the resolved Workday supplier name. On enrich, when the match is the supplier already on the invoice, that supplier's name is the last fallback.
- A generated number with no document invoice date is left unset. Wire, individual, and SIR expense-report formats are not applied; enrichment has no payment-type or person signal for them.
- The Workday note still records the document value (`Supplier Invoice Number (from document)`). Slack `*Supplier Invoice #*` is the number submitted to Workday.

When Workday says the supplier's invoice number is already in use (`Enter a Supplier's Invoice Number that isn't already in use`, XPath `Suppliers_Invoice_Number`), submit fails with the original Workday validation message. It does not retry on the fallback supplier or append a timestamp. The document number stays in the Workday note. Create and enrich Slack still show that duplicate-invoice-number message.

If the ISU is missing it, Workday returns `SOAP-ENV:Server.processingError` / `The task submitted is not authorized`; cache keeps previously stored `relatedLob` metadata (even if the follow-up Postgres related-LOB read throws) and does not Slack on every failed run. ## Workday supplier invoice payload

Tax and freight/shipping/handling are header amounts, not invoice lines, on any invoice that also bills goods or services:

- `Tax_Amount` comes from `extractedTaxAmount`
- `Freight_Amount` comes from `extractedFreightAmount` (PDF labels may be freight, shipping, handling, or delivery)
- Enrichment also returns `extractedFreightLabel` and `extractedTaxLabel`. `normalizeExtractedFreightAndTax` in `src/lib/invoice_lines.ts` corrects mislabeled amounts before submission: a freight amount labeled "Sales Tax" moves to tax, and a tax amount labeled "Shipping" moves to freight. When only one label is crossed and its amount equals the other field (both labels say tax, or both say freight), it is the same row read twice and is dropped; when it differs, both amounts are kept as read and the invoice notes get a `Freight/Tax review` line for AP. When both labels are crossed, the two amounts are swapped even if they are equal, since they are two printed rows.
- A cleared header (the normalizer moved its amount away, or the document shows a labeled zero) is submitted as an explicit `Freight_Amount` 0 or `Tax_Amount` 0, so an OCR value on an existing draft is overwritten rather than kept. Only cleanly parsed non-negative amounts are submitted, swapped, or cleared: US digit grouping (`8,514.38`), an optional leading or trailing currency symbol or code from exactly `$`, `€`, `£`, `¥`, `USD`, `EUR`, `GBP`, `JPY`, `CAD`, `AUD`, `CHF`, `CNY`, `INR`, and trailing footnote marks (`*`, `†`, `‡`). A blank or whitespace-only amount counts as not read. Any other amount (negative, locale-formatted like `1.234,56`, another currency like `SEK 510.86`, or text) is withheld because the Workday builder's `parseExtractedAmount` strips signs and separators and would submit a different number. A withheld amount leaves the existing Workday value in place (the draft's current header, or for freight the draft's own OCR freight rows, as when nothing was extracted), and the invoice notes get a `Freight/Tax review` line naming it. When one amount is withheld, a crossed-label amount on the other field is withheld too rather than submitted under the wrong field. `resolveHeaderChargeAmounts` wraps the normalizer for both create and enrich and fills freight from freight lines only when no freight header amount was read, so line freight never replaces a withheld header.
- A printed zero freight header is the one case where freight rows refill a cleared header: when the header freight was cleared but the freight rows carry an amount and goods + those rows + tax equal the amount due, `restoreClearedFreightFromRows` uses the row total as the invoice freight and the `Amount check` note says so. `prepareInvoiceCharges` then decides where it goes: header `Freight_Amount` on a mixed invoice, or the coded freight line on an all-freight invoice, so the restore sentence does not name either. Otherwise the stripped freight rows would leave the invoice short of the control total.
- Those charge rows must not appear in `Invoice_Line_Replacement_Data`

All-freight invoices (carrier bills, shipping-only invoices) are the exception: when no goods remain and freight + tax is the whole amount due, freight is submitted as coded invoice line(s) and header `Freight_Amount` stays empty. Header freight carries no worktags and Workday only allocates it to lines whose spend category allows it, so with no goods lines it would post uncoded. `prepareInvoiceCharges` in `src/lib/invoice_lines.ts` decides this for create and enrich and passes `freightAsLines` to submit; `buildSubmitInvoiceData` in `src/lib/workday.ts` then keeps those lines and clears any OCR `Freight_Amount`. Enrichment that only annotates keeps header freight.

When the submitted header `Tax_Amount` is greater than zero (from `extractedTaxAmount`, or the existing Workday `Tax_Amount` when nothing is extracted), each line built from `finalLines` carries `Tax_Applicability_Reference` with `Tax_Applicability_ID` `TAX_APPLICABILITY-3-2` (USA Taxable), including the synthesized update remainder `Invoice` line. Discount lines (`isDiscountLine`) never carry it, and OCR passthrough lines kept on update are left as Workday returned them. The header stays `Default_Tax_Option_Reference` `ENTER_TAX_DUE` with no line tax code. If Workday returns a validation fault that references `Tax_Applicability` (or a line `Tax_Code_Reference` xpath) while a submitted line carries the reference, submit retries once without it and records the `omitted line tax applicability` fallback.

If the PDF lists shipping/handling as a line item, capture the amount on `Freight_Amount` and omit that row from the SOAP line payload. `splitFreightLines` in `src/lib/invoice_lines.ts` strips those rows before merge/PO matching and again when building the SOAP body. The matcher treats carrier-only service labels (`FedEx Ground`, `FedEx Home Delivery`, `UPS Ground`) and common service words (`standard`, `priority`, `2-Day`, `air`/`ocean` freight, `surcharge`, `freight in`/`out`) as freight, and still rejects merchandise lookalikes (`Shipping Container`, `Freightliner parts`, `Shipping Supplies`). Carrier rows that lead with a pro number (up to four letters, five or more digits, up to two letters) and print the billed weight are freight too (`FRN52118A - Freight Charge - 42,000.00 Pounds`); item codes such as `SKU123` stay merchandise. Amount recovery reads SOAP `Unit_Cost` and `Quantity` when `Extended_Amount` is missing.

Additional tax rows besides the main tax are read by OCR into `extractedOtherCharges` (label and printed amount, never computed from a rate). A second row whose label says tax (`5% EnvChg Tax`) belongs there even when it is a row in the line table. Non-tax fees (fuel, service) are not listed there and stay where they were before: freight in the freight fields, a row printed only in the totals block in `extractedSummaryCharges`, everything else as lines. `applyPrintedTaxCharges` (`src/lib/header_charges.ts`) runs in create and enrich after `resolveHeaderChargeAmounts` and before `prepareInvoiceCharges`. A charge is tax-like only when its printed label says tax (`isTaxLikeChargeLabel`: a tax word such as tax, VAT, GST, or HST, and no tax-metadata word such as ID, rate, or exempt); `EnvChg` alone, fuel, service, and other fees are never moved. A row that restates the header tax (the same label as `extractedTaxLabel`, or a total row) with the same amount is skipped, but two different taxes with equal amounts both count. A tax-like charge is added to the header `Tax_Amount` only when lines + freight + tax fall short of the amount due by exactly those charges (all of them together, or the single one that equals the gap). A charge that repeats the tax already read, a credit or unparseable amount, and a gap no printed charge explains are left alone, so the amount check reports them. The change is named in the `Amount check` sentence (`Added "EnvChg Tax" $17.00 to header Tax_Amount ...`) and the `Tax Amount (from document)` note lists the parts. Example: lines $180.50 + $162.00, Sales Tax $28.26, EnvChg Tax $17.00, amount due $387.76 submits `Tax_Amount` 45.26.

Totals-block rows that are not freight or tax (`Decoration $5.00`, `Merchandise Discount $13.80`) are read by OCR into `extractedSummaryCharges` (label and amount as printed, keeping a printed minus sign or parentheses; an empty amount when only a rate is printed). Part 9 is unchanged and reads the line table, so before this field a fee or discount printed only next to Sub Total was dropped (SUPIN-470485 submitted $307.68 of a $312.68 invoice). If the model also reads a totals row as a line, the repeat check below skips the totals copy. Part 5.7 excludes applied credits, credit memos, retainers, and refunds. `placeSummaryCharges` (`src/lib/header_charges.ts`) runs in create after `removeRepeatedLineTables` and in enrich when it submits lines, and is skipped for a withheld charge, freight sent as lines, or a dropped row. Rules:

- Rows are ignored when they are subtotals, totals, payments, deposits, or balances (`Sub Total`, `Merchandise`, `Grand Total`, `Amount Paid`), freight (`labelMatchesFreight`, `S&H`), tax (`isTaxLikeChargeLabel`), a charge for the same amount as header freight or tax, or a repeat of a line (same amount and a shared label word, or a negative line for a discount). `Merchandise Discount` and `Decoration Total` are not summaries.
- Applied credits are never added: a label with credit, memo, retainer, or refund (`Credit Applied`, `Less Credit Memo 4411`, `Less Retainer`; not `Credit Card Fee`) settles the bill rather than lowering the cost of the goods, and the credit may already be its own document in Workday. When the invoice does not reconcile, the note names the row and asks AP to check whether the credit is already in Workday.
- Sign: a printed minus or parentheses is a credit and is never flipped. A label that starts with `Less` (`Less Early Pay`) counts as a printed minus. A discount-style label (discount, allowance, promo, rebate, coupon, markdown; not when the label also says fee or charge) printed unsigned is a credit by default. Anything else is a charge.
- Exact match only: rows are added as invoice lines when lines + freight + tax miss the amount due by exactly all of them together, or by exactly one row. Nothing is added when the lines would drop to zero or below.
- An unsigned discount whose credit reading does not close the gap but whose charge reading does (alone, or with the other rows) is not added, and the note gives both readings (`"Merchandise Discount" $13.80 was not added: as a credit, ... $70.20; as a charge, $97.80, which matches the amount due.`). Whenever the gap is not zero, every row that was read but not added (a row neither sign explains, an applied credit, a rate-only row) is named in the note, including when another row was added. A gap of zero adds and notes nothing.
- Added rows are `ExtractedInvoiceLine`s (amount only, `hasDiscount` on a credit) that go through the normal merge for coding. `settlePlacedSummaryLines` then drops any PO line link from each added row it finds (coding kept). When every added row is a submitted line, the `Amount check` says so (`Added "Decoration" $5.00 from the invoice totals as an invoice line ...`, plus `It is not linked to a PO line.` when it had one). When the merge or an email budget split folded a row into other lines (for example two email budgets that now match the $287.50 base), the `Amount check` names the row as included in the submitted lines but not as a separate line, as long as the submitted lines total what was read. Otherwise the review note asks AP to check the lines. A negative line is a discount line in Workday (`isDiscountLine`): `Quantity` 0, no PO link, no tax applicability. A placed discount beside lines on more than one cost center adds a coding review sentence. Rows not added go to `Totals charge review:` in the Workday note and Slack line review.
- Example (SUPIN-467235): lines $69.00 + Decoration $5.00, freight $10.00, unsigned `Merchandise Discount` $13.80, amount due $70.20 adds a -$13.80 line; with amount due $97.80 nothing is added and the note gives both readings.

**Repeated rows, the printed line total, and deposit invoices (SUPIN-470584).** Activity Planners' deposit invoice 2130B printed 28 rows under event-day headings, `Total Cost of Contracted Services` $38,255.00, `Deposit Required Upon Signing 90%`, and `Advance Deposit Due` $34,429.50. The OCR model returned 27 rows: "Fresh Cut Floral Centerpieces" 30 x $135.00 is printed under Tuesday and Wednesday and was read once. Nothing after OCR removes a row (the merge prompt requires one output line per input line, and `removeRepeatedLineTables` only drops a whole extra table), so the drop was the model's. The invoice then billed $34,205.00, which is not the deposit, and it was linked to the PO's $3,825.50 balance line instead of its $34,429.50 deposit line.

- **Keeping repeated rows.** Part 9 of the OCR prompt tells the model to return every printed row in document order, and that identical rows under different dates, events, or headings are separate charges. Each row carries `sectionLabel` (the heading it is printed under; a required string, empty when none). It is not part of `Item_Description` and never sent to Workday; it exists so identical rows are distinguishable to the model and in logs. Rows under different headings in one table share one `tableNumber`.
- **Printed line total.** `extractedLineSubtotal` (`label`, `amount`; required strings, empty when not printed) is the total the document prints for its line-table rows before freight, tax, discounts, and any deposit. Prompt Part 4.5 covers it. The OCR schema stays at 3 union-typed and 0 optional parameters.
- **Missing-rows retry.** `extractInvoiceDocuments` compares the extracted row totals with `extractedLineSubtotal`. When the rows fall short, it reads the documents once more with an instruction naming the first read's row count and total and the printed total. The second read replaces the first only when it keeps every first-read row (same description and total, counted as a multiset, so it can only add rows) and its rows total the printed line total to the cent; otherwise (a changed or dropped row, still short, overshoot, no printed total, a row with no total, an OCR error) the first read stands. An abort during the second read throws. The retry is skipped when any first-read row has `hasDiscount` (a net-of-discount row never reaches a subtotal printed before discounts) and when the caller passes `retryMissingRows: false` (`EnrichInvoiceProcessor` does when it cannot modify the invoice). Each retry logs `Invoice OCR missing-row retry` with `outcome`, `checks` (`amountDue`, `subtotal`, or both), `amountDueShortfallCents`, and `subtotalShortfallCents`, so how often each check fires and is accepted can be watched after deploy. `outcome` is `accepted`, `rejected`, or `failed`. It adds one OCR call (about 25 seconds) only on a shortfall. `CreateInvoiceProcessor` times out at 420 seconds and `EnrichInvoiceProcessor` at 300 (`template.yml`), so check the slowest enrich path before relying on the retry there. **Amount-due gap (SUPIN-472108).** A printed section total can cover only part of the table (an `Agreement Subtotal` that leaves a printed `Fuel` row out), so the retry also triggers on `amountDueGapCents` (`src/lib/partial_payment.ts`): amount due less the rows, printed freight, tax, and other charges. A positive gap not explained by a totals-block row (`amountDueShortfallCents`) asks for a second read with the gap in the instruction; that read is accepted only when it keeps every first-read row, every added row is non-negative, and the added rows total the gap to the cent (or the retried rows total the printed subtotal). A gap of exactly zero means no retry even when the subtotal is short. The gap is not computed for deposit or prior-payment invoices. A `N/C`, `Included`, or similar no-charge row (`isNoChargeAmount`) counts as $0 in row sums instead of making them unreadable; before this, such a row disabled the subtotal retry and note. The OCR prompt (Parts 4.5, 5, 9) keeps a single freight charge in `extractedFreightAmount` but tells the model to return several separate delivery, pickup, or return rows as lines; a delivery row stays header freight through `splitFreightLines`, while `PICKUP CHARGE` has no freight token and stays a merchandise line. **Freight inside the subtotal and unlined discounts (SUPIN-472322).** A printed `Subtotal` can already contain the freight (`$48,102.66 - Discount $8,866.66 + Tax $2,354.16 = $41,590.16` with `$2,000.00` freight inside). `subtotalFreightCents` (`partial_payment.ts`) decides from the document's own arithmetic: freight is inside when subtotal, less credits, plus tax and other charges equals the amount due without adding freight. The subtotal target for the rows is then the subtotal less that freight (`lineSubtotalShortfallCents` third argument; `MissingRowsPlan.subtotalRowsCents`), so the gap is `$1,388.00`, not `$3,388.00`. Unlined discounts count too: `summaryCreditCents` (`header_charges.ts`, built on the same candidate rules as `placeSummaryCharges`) totals totals-block rows that reduce the bill (printed minus or parentheses, a leading `Less`, or an unsigned discount label), and `amountDueGapCents({ creditCents })` applies them only when the rows overshoot the amount due and the credit brings the gap back to zero or above (Joe's rule: an unsigned discount is negative if negating it reconciles). Without that, a first read that missed rows and had no discount line showed a negative gap and no retry ran. Once the second read adds the rows, `placeSummaryCharges` reconciles and places the discount as a negative line as before. The SUPIN-472322 production log shows the old subtotal-only acceptance rejected the second read (rows could never reach the printed subtotal) after a 144-second second read inside a 329-second run, so watch the 420-second Lambda timeout.
- **Second-read rows are disclosed.** When a second read is used, the rows it added ride on `extractedRowsAddedOnSecondRead` (set by code, never the model) and `secondReadRowsNote` puts `A second read of the document added a row the first read missed: ...` in the `Line subtotal review:` note (Workday note and create Slack *Line review*), so AP checks them against the PDF.
- **Line subtotal review.** `lineSubtotalReviewNote` (`src/lib/partial_payment.ts`) compares the rows as read, before freight, tax, and repeated-table removal, with `extractedLineSubtotal`. A mismatch adds `Line subtotal review:` to the Workday note and the create Slack *Line review*. When the gap equals a row's amount it names that row ("check whether that row is printed more than once"); rows are never added from it. It is skipped when a `Repeated line review` removed a table, when the document prints no readable total, or when a row has no total. Create and enrich both run it (enrich only when it submits lines). `lineSubtotalReviewNote` also takes the amount-due gap: a gap of exactly zero suppresses the note (the printed total covers only part of the table), and a positive gap that differs from the subtotal gap says `Lines, freight, and tax are $X short of the amount due, so charges that the document prints (for example delivery, pickup, or other rows) were probably not read`. Create and enrich build the gap with `reviewAmountDueGapCents`, which passes totals-block rows and the other charges not folded into tax, and reads a gap that a totals-block row explains as zero (that row is placed as a line, so the note must not say rows were missed). They skip the gap on deposit, withheld-charge, freight-as-lines, and prior-payment invoices. This changes only OCR rows and review notes; every invoice is still sent with `Submit: false`. `lineSubtotalReviewNote` takes a fourth argument, the freight inside the printed subtotal, and then compares the rows with the subtotal less that freight (`... $48,102.66 as "Subtotal", $46,102.66 without the $2,000.00 freight it includes`); a zero difference gives no note.
- **Deposit detection.** `extractedPartialPayment` (`label`, `percent`, `amount`; required strings) is the deposit or advance row the invoice bills instead of the contract total. Prompt Part 4.5 excludes `Less deposit paid`, retainers, and ordinary invoices. `planPartialPayment` (`src/lib/partial_payment.ts`, create and enrich) applies it only when all hold: the label has a deposit word (deposit, advance, down payment, prepayment, installment, progress, partial) and no already-settled word (less, paid, applied, received, credit, balance, remaining, previous, retainer, refund), otherwise nothing happens at all; the deposit equals the amount due to the cent; header freight and tax are not printed; the contract total (`extractedLineSubtotal`, else the sum of the extracted rows) is larger than the deposit; a printed percentage below 100 reproduces the deposit from the contract total within one cent (the percentage is only a cross-check, nothing is computed from it); and the PO check below passes. A deposit label that fails a check is not applied and says why (`Deposit invoice: "..." looks like a deposit or partial payment, but ..., so the printed lines were submitted unchanged.`, plus a Slack *Deposit* line); the normal amount check still runs.
- **How it is booked.** One extracted line replaces the printed rows: quantity 1, unit cost and total the printed deposit, description `<label> (<pct> of <contract total>)` (`Advance Deposit Due (90% of $38,255.00)`). `invoiceLineQuantityDisplayed` is forced to true so the line counts as one unit on its PO line. `removeRepeatedLineTables` and `placeSummaryCharges` do not run, and the pre-submit amount check is cleared because the submitted line equals the amount due; the submit-time check still reconciles the real payload. The merge codes the line like any other line.
- **PO line.** When the PO has lines, `selectDepositPoLine` needs exactly one line whose amount (`Extended_Amount`, else quantity x unit cost) equals the deposit; an open line wins over a consumed one with the same amount, and a lone consumed line is pinned so the existing consumed-line logic drops the reference. In that case the deposit note and Slack *Deposit* section say the PO line is already fully invoiced or closed, so AP checks whether the deposit was billed before. That line is the only PO line passed to the merge. No such line (none, or several open) means the deposit is not applied, since the coding would be a guess. With no PO lines the deposit line is coded like any other line without a PO.
- **Notes and Slack.** The Workday note gets `Deposit invoice: "Advance Deposit Due" $34,429.50 is 90% of $38,255.00 for the contract total (28 printed lines). The invoice bills the deposit, so it was submitted as one $34,429.50 line instead of the printed lines. The full line list is below and on the attached PDF.`; `Invoice Lines (from document)` still lists every printed row. The note does not claim the PO link, which a repair retry can drop; the existing PO fallback note reports what Workday accepted. Create Slack shows `*Amount Due* → $34,429.50 (90% deposit of $38,255.00)` and a `*Deposit*` section. Enrich Slack does not show the deposit section; its note does. The invoice is still created as a draft (`Submit: false`).
- **AP's rule (confirmed by AP, 2026-10-22).** When a deposit invoice is paid, AP codes it to one PO line and uses one SUPIN line, whatever the number of lines on the quote or invoice, because only the lump-sum deposit matters. AP does not pay tax on a deposit; a printed tax is paid with the balance invoice. So a deposit invoice that prints tax is not applied (the reason says so) until someone confirms whether the amount due includes the tax. Scaling every line to the percentage and Workday's down-payment flag were rejected. The final invoice for the balance, which prints `Less deposit paid`, is not changed by this. Not yet confirmed with AP: a deposit invoice with no PO (the agent still submits one deposit line coded like any no-PO line) or with no PO line for the deposit amount (the lines are left as printed).
- **Related work.** A deposit is never a totals-block charge (`placeSummaryCharges` keeps ignoring `Deposit` rows); a future balancing line for an unexplained gap must measure from the deposit amount when a deposit was applied.

**Remaining-balance invoices (SUPIN-471692).** The Convention Store invoice printed `Total Contract Price` $23,887.00 and a $5,909.50 balance due, and the email split $5,909.50 across two budgets ($5,279.50 + $630.00). The agent booked the $23,887.00 line, `applyEmailBudgetSplits` rejected the split (the lines did not equal the amount due), and the line fell back to default coding. OCR had excluded settled payments everywhere, and nothing recorded that the email called the amount a remaining balance.

- **Signals.** OCR returns `extractedPriorPayments` (array of `label`, `amount`; empty when none is printed; Prompt Part 4.5): payments, deposits, or credits already received, never `extractedPartialPayment`. Matching returns `emailBalanceDue` (`amount`, `phrase`; required-nullable) only when the email explicitly calls the amount to pay the remaining balance or final payment; the model never computes it, and a dollar amount assigned to a budget is a split, not a balance. Arrays add no union types to the OCR schema, so the limits in `invoice_ocr.test.ts` still hold.
- **`planBalanceInvoice` (`src/lib/partial_payment.ts`).** Runs in `create_invoice.ts` and `enrich_invoice.ts` only when no deposit plan, no withheld charge, and no freight-as-lines apply, and after `removeRepeatedLineTables` and `placeSummaryCharges`, so their explanations of a gap win. It needs the contract total (the printed line total, else the line sum) and the lines to both exceed the amount due, plus one signal: printed payments that satisfy contract - payments = amount due to the cent, or an `emailBalanceDue` equal to the printed amount due to the cent with a non-empty phrase, which counts only when the document also prints a contract total (`extractedLineSubtotal`), because a line sum can read high for other reasons. The prompt triggers on "remaining balance" and "final payment", not a bare "balance due", which most invoices print. No signal returns undefined and nothing changes.
- **How it is booked.** One quantity 1 line at the printed amount due, described `<label> (balance due of <contract total>)`, replaces the lines and any placed totals charges, `invoiceLineQuantityDisplayed` is forced true, and the amount check is cleared. The email budget split then applies to that line, since `budgetSplitOptions` bases the split on the amount due. The line is built through the same code for create, enrich, and the conversation resend update.
- **Not applied, with a note.** The printed lines are submitted unchanged and the Workday note (`Balance invoice: This looks like a remaining-balance invoice, but <reason>...`) and Slack `Balance invoice` section say why when: printed payments exist but do not reconcile and the email does not match, tax or freight is also printed (v1 does not book those), or the PO has lines and none equals the balance (`selectDepositPoLine`, same rules as a deposit, including the consumed-line warning). With no PO lines the balance line is booked without a PO link. A PO that failed to load counts as no PO lines.
- **AP rule: not yet confirmed.** Unlike the deposit rule, AP has not confirmed that a balance invoice is one SUPIN line at the amount due. Open case: a PO with one line for the full contract, part of it used by the deposit invoice, will get the `no PO line is for $X` note and keep the printed lines; whether AP wants those coded to the partly used line is undecided.
- **Notes.** The note describes what was submitted (`"Total Contract Price" is $23,887.00 but the amount due is $5,909.50, and the email calls $5,909.50 the remaining balance`), and says when the document prints no payment that accounts for the difference. The invoice is still a draft (`Submit: false`).


Workday's gross amount is lines + `Freight_Amount` + `Tax_Amount`, so a charge must not be both a header amount and a line. `reconcileSubmittedCharges` (`src/lib/invoice_lines.ts`) compares lines + freight + tax with the amount due, at extraction (`prepareInvoiceCharges`) and on the lines actually submitted (`resolveSubmittedCharges` in `src/lib/workday.ts`). Invariants:

- Totals that already reconcile are left alone, so legitimate header-only freight stays.
- A line is dropped only when the excess is exactly the header freight and/or tax and the dropped lines are freight (`isFreightOrHandlingLine`) or tax rows summing to it. Goods are never dropped; an unrecognized single line equal to the header freight is kept as the line with no header freight, and the note asks AP to check the extracted freight instead of calling it a freight bill.
- When the PO merge returns no line for an all-freight invoice, create and enrich rebuild it without the PO. Submit keeps freight as lines only when the submitted lines plus tax equal the control total; otherwise it falls back to header freight and the note drops the freight-as-line sentence (`mergeAmountCheckMessages`).
- Anything else is submitted as extracted and flagged once, from the submitted payload. A flagged gap (`but the amount due is`) is also made hard to miss: the Workday note leads with the `Amount check:` block, the create Slack headline is `⚠️ ... created ... with an amount mismatch` instead of `✅`, and, when `WORKDAY_AMOUNT_MISMATCH_TAG_WID` names an existing Work Queue Tag, create adds that tag next to the agent-modified tag. The env var is unset by default; an unknown tag ID would fail the submit, so set it only after the tag exists in Workday. The tag is chosen from the lines and charges before the submit repair loop runs; if a repair later changes lines or freight, the tag and the final note can disagree, so check that (or re-evaluate after repair) before setting the variable.
- Printed credits count as negative; unparseable row amounts count as zero.

Removals and mismatches reach the Workday note (`Amount check:`) and Slack (*Amount Check*, escaped, one section per line) through the `chargeReconciliation` applied fallback, not `Fallback values applied`. Logs carry counts only.

When the invoice document does not display a per-line quantity column (`invoiceLineQuantityDisplayed: false` from enrichment, or inferred when the model omits the flag and every extracted line has null quantity and at least one line amount), merchandise lines submit as `Quantity: 0`, `Unit_Cost: 0`, and `Extended_Amount` from the line total (`extendedAmount`, or `unitCost` when extended amount is missing) — including synthesized update remainder `Invoice` lines. If any extracted line has a quantity, the document is treated as quantity-displayed regardless of the model flag. Explicit `true` from the model is not overridden. This is distinct from discount lines, which use the same SOAP amounts but drop `Purchase_Order_Line_Reference`. A discount line (`isDiscountLine`) has a negative line amount (`extendedAmount`, else `unitCost`), whatever `hasDiscount` says, so a credit row with no discount marker never invoices PO line quantity; or it has `hasDiscount: true` and a line amount that is zero or missing. Enrichment also sets `hasDiscount` on merchandise rows that print a discounted net total; a positive row is merchandise, so it keeps its quantity, `Purchase_Order_Line_Reference`, and line tax applicability. Workday only records a PO line as invoiced when the invoice line carries that reference and a quantity.

Do not invent unit cost from quantity and line total. Enrichment and merge must leave `unitCost` null when no unit price is printed (the one exception is the single-price reading below, which code decides before the merge). After merge, `alignSupplierInvoiceLineAmounts` submits `Quantity: 0`, `Unit_Cost: 0`, and `Extended_Amount` from the printed line total when unit cost is missing or `quantity * unitCost` (SOAP uses quantity `1` when quantity is null) does not equal extended amount to the cent. Exception: a line flagged as discounted (`hasDiscount: true`) and linked to a PO line (`purchaseOrderLineId`) with a positive quantity submits the net unit cost (`extendedAmount / quantity`, rounded to four decimal places) with the printed quantity when the net unit cost is below the printed unit cost and reproduces the line total to the cent (for example `45 x 46.50` printed with a `1966.95` total submits `45 x 43.71`), so Workday counts the PO quantity as invoiced. Any other mismatch falls back to amount-only. Matching qty / unit / extended triples keep their values apart from the decimal rounding below. `normalizeSupplierInvoiceLineAmounts` runs the missing-quantity-column shape first, then this alignment, in both create and enrich.

**Single price beside a quantity (`reinterpretSinglePriceLinesForCharges`, `src/lib/header_charges.ts`).** A line can print a quantity and one price that is really per unit, with no line total (SUPIN-471803: quantity 9, one `$75.00`, amount due `$675.00`). OCR reads that price as `totalPrice` with `unitCost` null, so the line would submit amount-only at `$75.00` and the Amount check would flag a `$600.00` gap. Create and enrich run the step on the extracted lines right after `resolveHeaderChargeAmounts` and before `restoreClearedFreightFromRows`, `applyPrintedTaxCharges`, and `prepareInvoiceCharges`; it never runs in OCR or the merge. An eligible line has a quantity above 1, no `unitCost`, no `hasDiscount`, a positive printed `totalPrice` (not a credit), a description that is not freight or tax, and a quantity x price that is a whole-cent amount. Nothing changes when the lines as read already reconcile: the check counts restored freight, duplicate freight and tax lines, printed tax-like charges, and totals-block charges. A totals-block charge counts only when the caller will place it (`summaryChargesPlaceable`: no printed row was dropped; an eligible line is never freight, so freight sent as lines cannot reach this point), so the reading never claims a reconciliation the later steps will not make. Enrich skips the step on annotate-only runs (`INVOICE_MOD_ENABLED=false` or no supplier to submit), since no line changes there and the Amount check must stay. It does nothing when a header charge is withheld or the amount due is unreadable. Otherwise it tries every subset of eligible lines (at most 8 eligible lines) and takes a reading only when exactly one subset reconciles; zero or several leave the lines alone, so the `Amount check` flag still fires. On a match the line keeps its quantity, `unitCost` becomes the printed price, and `totalPrice` becomes quantity x price, so the normal merge and `alignSupplierInvoiceLineAmounts` submit quantity, unit cost, and extended amount that agree. A `Line price review:` sentence goes to the Workday note (and the create Slack *Line review*) naming the reading. It does not claim the submitted Quantity or Unit_Cost, because a PO-linked line can still go amount-only. The `Invoice Lines (from document)` note keeps the printed values.

Before that check, alignment rounds every line to the WSDL decimal limits: `Quantity` to two places and `Unit_Cost` to six. Rounding works on the decimal value, with halves away from zero, so `1.005` rounds to `1.01` and `-12.345` to `-12.35`. An `Extended_Amount` with up to three decimals (the WSDL limit) is kept as printed, and a longer one rounds to cents. A non-discount line with no extended amount whose quantity or unit cost was rounded first records the cent total of the unrounded `quantity * unitCost` as its extended amount. Lines flagged `hasDiscount: true` are rounded like any other line but never get that recorded total, because the builder submits discount lines amount-only with `extendedAmount`, else `unitCost`. A negative line with no discount marker and no extended amount always records the cent total of `quantity * unitCost` (quantity `1` when null), so going amount-only keeps the total Workday would have computed from its quantity. The cents check then runs on the rounded values, so rounding never changes a line total to the cent. A printed back-computed rate such as `24.45 x 224.9488753 = 5500.00` submits `24.45 x 224.948875`, and a line whose rounded quantity and unit cost no longer reproduce the total (for example `2.555 x 1000` with no printed total) falls back to amount-only with that total. When the line merge fails and extracted lines are used directly, `parseExtractedUnitCost` keeps six decimals instead of rounding the unit cost to cents. That fallback reads the unit cost and line total (`parseExtractedLineAmount`) as signed, so a minus sign before the first digit or a parenthesized amount (`-$250.00`, `($250.00)`) stays negative and a discount row is not submitted as a charge. `parseExtractedAmount`, used for the header amount due, freight, and tax, still drops signs. The merge prompt also tells the model to keep every printed unit-cost decimal.

**PO unit cost and rounding.** `FinalInvoiceLine.purchaseOrderLineUnitCost` (set with `purchaseOrderLineQuantity` by `overlayPoWorktagsFromPurchaseOrder`, cleared when a line is detached from the PO) lets `alignSupplierInvoiceLineAmounts` keep a quantity-split PO line's printed quantity when its total misses `quantity x PO unit cost` by a unit price with more decimals than the PO's (Semicolon 26-2177 on PO-414547: 54 printed at 12,888.71 against a PO price of 238.68). Instead of going amount-only, the line submits the printed quantity with `unitCost = total / quantity` (six decimals) and sets `unitCostFromLineTotal`. It requires a linked, non-discount line whose PO line is split by quantity, a positive quantity no larger than the PO line quantity, an implied unit cost less than $0.01 from the PO unit cost (a per-unit bound, so a real price change is never absorbed), and `quantity x implied unit cost` equal to the total to the cent. Anything else keeps the amount-only rules above, and non-split quantity PO lines keep the one-unit rule because nothing here knows what is still open on a partly invoiced PO line. The linked split lines then send the PO split quantities (`allocateSplitQuantities`) priced from the total. `create_invoice` and `enrich_invoice` add `unitCostFromLineTotalNote` to the PO line quantity review note; it is built before submit and does not claim the PO link.

**Ship To faults.** `isInvalidShipToAddressError` matches "The Provided Ship To Address is Invalid for this Supplier Invoice Document" (it does not match the `Ship_To_Contact_Reference` fault). The repair loop handles it before the classifier: `invalidShipToAddressLinePositions` reads the `Invoice_Line_Replacement_Data[n]` rows the Ship To faults name (fault by fault, so a Ship To fault without an Xpath never takes another fault's row), and the `shipToAddress` fallback resends without `Ship_To_Address_Reference` on those payload rows (every row when none can be read), labeled `OMITTED_SHIP_TO_ADDRESS_LABEL`. It runs once and only when a submitted line carries a ship-to; a second Ship To fault fails. The submitted-lines log shows each line's `shipTo`, and the PO line log shows the PO line's ship-to, description (first 80 characters), and extended amount.

After alignment, create and enrich compare the sum of the submitted merchandise line amounts with the document amount due less the header freight and tax that will be submitted. Line amounts follow the SOAP builder: `extendedAmount`, else `quantity * unitCost`, with discount lines counted once at `extendedAmount` or `unitCost`, and freight-described lines moved to freight. Header charges also follow the builder: a cleared charge is zero, an extracted amount wins, and otherwise enrich uses the `Freight_Amount` / `Tax_Amount` already on the Workday invoice (freight then falls back to freight-described lines). When the two differ by a cent or more, `lineTotalMismatchNote` adds a `Line total review:` Workday note. When the lines exceed the expected amount, the note asks AP to check for a duplicated or summary line (for example a monthly-retainer row printed beside its hourly breakdown), or a payment, credit, or discount applied outside the lines, since enrichment reads only the amount due, not a separate invoice total. When they fall short, it asks AP to check for a missing line or charge. The note never drops or edits lines. The check is skipped when there is no amount due, no lines, a line without an amount (freight-described rows included), or only freight-described lines. It is also skipped when the amount due or a charge does not parse as a plain non-negative amount, so a credit memo with a negative or parenthesized amount due is not compared, or when a charge was withheld with its own review note (`chargeWithheld` from `resolveHeaderChargeAmounts`). It is skipped when `prepareInvoiceCharges` sends freight as lines, since that freight is not on the header and the submit-time `Amount check` reconciles that payload instead. Conflicting freight and tax that are both submitted are still compared. The create resubmission path does not read the existing draft's charges, so a draft charge that was not re-extracted can still produce a note.

Before the line merge, create runs `removeRepeatedLineTables` on the extracted merchandise lines. Enrichment numbers each row's source table (`tableNumber`, 1, 2, 3... in document order), because some invoices print the same charge twice, for example LevelBlue's hourly `Consultant` row (`24.45 x 224.9488753 = 5,500`) and its `Sep'26 | 5,500 per month` summary row. Rows are removed only when no extracted row was dropped for a missing description or amount, every row has a positive integer table number (numbered 1, 2, 3... with no gaps) and a non-negative amount (a printed total, or a printed non-negative quantity times unit cost, so a credit row blocks removal), no row has a blank description, `hasDiscount: true`, or a negative or non-finite quantity, the rows together miss the amount due less freight and tax, there are two or more tables, and every table on its own totals that expected amount exactly, and every table that states a month states the same set of months (a prior month's balance beside this month's charge is two charges; a table with no month, like an hourly table, can still restate one that has a month; a calendar-invalid date states no month; a numeric date is read as `MM/DD/YYYY` or `MM/DD/YY`, a two-digit year meaning 20YY, while a bare `MM/YY` or a fraction such as `1/2` is not a date). A printed line total (`extractedLineSubtotal`, passed in as `options.lineSubtotal`), when the document prints one, must equal each table's total, or nothing is removed (an unreadable one also blocks the removal); this applies whichever criterion would keep a table. Then one table is kept and the others are dropped. The kept table is the one with the largest share of rows that, in order: match an open PO line (`availableForInvoicing` not false) on `extendedAmount` and a stated month that the PO line's start and end dates span in full (one missing date counts as open; a PO line with neither date, or with a date that does not parse, never matches), with each PO line matching at most one row of a table; state a month and a 20xx year (`Sep'26`, `September 2026`, `2026 - September`, `09/2026`, or the month of a US date such as `03/01/2026`); or reproduce their total from the quantity times a printed unit cost with no more than two decimals (a rate worked back from the total does not count). If those three criteria do not separate the tables, one last tie-break (`hours_by_rate`, SUPIN-471364) applies only on proof that the tables bill the same work: every row of every table has a positive quantity and a printed rate of at most two decimals whose product is the row's total to the cent, the hours summed per rate are identical across all tables, and exactly one table has the most rows. That table (the itemized time entries) is kept and the summary of the same hours (a law firm's timekeeper summary beside its dated entries) is dropped, with `Kept table 2 because its rows itemize the same hours at the same rates as table 1.` in the note. A misread amount due alone cannot trigger it, because the tables must also bill identical hours at identical rates. Otherwise, with no criterion and no proof, nothing is removed, because a misread amount due could make two real charges look like a repeat. When the itemized rows print no rate or amount, extraction drops them before this check (`extractedLines.length < extractedRows.length` skips it), so the priced summary is the only table submitted. A `Repeated line review:` Workday note names up to five removed rows with their amounts, counts and totals the rest, and says why the table was kept. Anything less certain removes nothing, including untagged rows, a single table, lines that already total the expected amount, an unparseable charge, and a withheld charge (`chargeWithheld`), and the mismatch is left to `lineTotalMismatchNote`. A Closed or Pending Close PO gives no PO lines to this check. The enrich path does not run it. Both review notes also go to the create Slack success message under *Line review* as `lineReview`, except on skipped resends; at most five notes are shown, each escaped for Slack and truncated to its own share of the section without cutting an escaped character.

Each create or update submit attempt (`submitSupplierInvoiceWithRepair`) logs `Submitted lines for invoice ... (attempt N)` with every line's worktags, splits, spend category (`Spend_Category_ID=...`), `quantity`, `unitCost`, `extendedAmount`, and PO line reference, because Workday's read-back after submit can show different amounts than were sent (for example `Quantity` and `Unit_Cost` zero on lines linked to service PO lines). A retry whose lines match the last logged attempt logs `unchanged from attempt N` instead. The enrich notes-only annotate submit does not log lines.

If Workday still rejects submit with `Either Quantity and Unit Cost must equal zero or the Extended Amount must equal Quantity * Unit Cost`, or with `Decimal precision of N exceeded for Unit Cost` / `Quantity` (also matched as `Unit_Cost` or with `!**!` placeholders, or from that error's own xpath when the message names no field; each `Validation_Error` is checked on its own, including one inside a strong-soap `Error` envelope; an `Extended Amount` precision fault, or one whose xpath is outside `Invoice_Line_Replacement_Data`, is not matched; the flattened validation text is read only when no structured error carries a precision message), the submit retry loop zeros `Quantity` and `Unit_Cost` on every merchandise line that has (a non-zero quantity or unit cost) and an extended amount, then resubmits. That retry is matched from the validation message (not the field classifier). Discount lines are left unchanged. Lines that already have Quantity 0 and Unit Cost 0, or that have no extended amount, are not rewritten.

Create vs update when no merchandise lines remain:

- **Create** (`submitNewSupplierInvoice`): all-freight invoices arrive with `freightAsLines` (above). Otherwise, if amount due exceeds freight plus tax, synthesize a non-freight remainder line and keep header `Freight_Amount`. Create has no OCR lines, so do not send `[]`.
- **Update** (`submitSupplierInvoiceUpdate`): with `freightAsLines`, the freight `finalLines` replace the OCR lines. A resubmit without final lines (enrich with no extracted lines, or `update-invoice-supplier`) keeps the lines of an all-freight invoice whose header freight is empty, whose lines plus tax equal the control total, and whose extracted freight is missing, unusable, or equal to those lines, whether this agent submitted it or it is a Workday OCR draft of a carrier bill. Otherwise, if `finalLines` are all freight, keep OCR merchandise (freight stripped) so goods are not wiped. When OCR is also all freight, send a remainder `Invoice` line (control minus freight minus tax, floored at 0) so SOAP actually replaces the shipping row — strong-soap drops empty repeating `Invoice_Line_Replacement_Data` arrays, which would leave the OCR shipping line in place. Workday Get may return those header amounts as strings; parse them before subtracting so a string `Freight_Amount` is not treated as 0.

Workday Get / strong-soap may return a single line as an object rather than an array. Unwrap with `[].concat(...)` before `splitFreightLines` so freight-only create still omits the line payload and freight-only update still replaces that row with a remainder `Invoice` line.

Submit logging must not include `client.lastRequest` or raw strong-soap error
objects. Those structures contain attachment bytes and the HTTP Authorization
header. Log request byte count plus a safe error summary, and throw a new error
containing only the original name/message.
For attachment submissions, log redacted outbound headers and only the SOAP
envelope `Header` element.

## Attachment bytes

- Intercom CDN → binary `Buffer` → `putBinaryToS3`
- Download URL must be `https` on `intercomcdn.com` / `*.intercomcdn.com` or `intercom-attachments-<n>.com` / `*.intercom-attachments-<n>.com` (SSRF allowlist); `fetch` uses `redirect: 'error'` so redirects cannot leave that host
- Only `application/pdf`, `.docx`, and `.xlsx` attachments are accepted; none of those → 400 `No PDF, DOCX, or XLSX attachment found on conversation`
- **Word and Excel files are stored and attached to Workday as the original file** (same name and content type; `Attachment_Data` carries the original bytes). They are converted to PDF in memory only where the AI model reads documents: `extractInvoiceDocuments` (`src/lib/invoice_ocr.ts`) and `classifyInvoiceAttachments` (`src/lib/invoice_attachment_clustering.ts`), both through `toModelDocument` in `src/lib/office_to_pdf.ts`. The converted PDF is never stored. `convertOfficeToPdf` is a text-and-table rendering (mammoth for docx, exceljs for xlsx, pdfkit for output), not a faithful print. Hidden sheets are skipped; long sheets paginate with repeated headers; wide sheets split into column groups; row caps are logged; output stops at 60 pages with an `[Output truncated…]` line so it stays inside the models' PDF limits. A nested Word table is flattened into its outer cell. Excel numbers are shown the way the cell's number format shows them (`formatNumberCell`: currency, percent, fixed decimals, thousands separators, parenthesized negatives; dates, fractions, and scientific formats fall back to a plain rounded number), and a formula cell shows its cached result. Each stored buffer is converted once per run (`toModelDocument` caches by buffer), shared by classification and OCR. A file that cannot be opened (corrupt or password-protected) is never read by the model: OCR leaves it out of the document list and roles, classification receives `N-name: unreadable document` and `parseAndClusterInvoiceAttachments` forces it to `supporting` with its keys cleared, and `processInvoiceCluster` stops with an error Slack post (`could not be opened … no invoice was created`) when the invoice (first) file is unreadable, so the agent never drafts from the email text alone. An unreadable backup file does not stop the invoice; it is still attached to Workday and the success Slack post lists it under `*Not read*`
- Max individual and combined download size is 20MB; downloads use at most four
  concurrent requests; trigger Lambda timeout is 30s with 1024 MB memory
- Attachment names are sanitized to a basename before the S3 key
- Processor Event payload is metadata only (no file bytes)
- Each Workday invoice receives its vendor PDF(s) as `Attachment_Data` (invoice first; a cluster's PDFs when clustering is on), with the conversation transcript appended last. `buildSubmitInvoiceData` reverses that list in `Attachment_Data` because Workday lists attachments newest-first, so the invoice is shown first. Each `Submit_Supplier_Invoice` call sets the full attachment list (omitted files are dropped), so resend updates send every cluster PDF plus a fresh transcript
- Success Slack details include filename, content type, byte size, and
  `includedInline`; never include base64 content
- Success Slack details include `conversationId` / Intercom conversation URL
  for create-invoice, and `priorFailures` when submit retried before succeeding
